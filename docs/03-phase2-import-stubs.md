# 03. Phase 2 — DLL-заглушки консольных импортов

## Постановка

После Phase 1 загрузчик Windows доходит до разрешения импортов и останавливается
с `STATUS_DLL_NOT_FOUND (0xC0000135)`: import-таблица ссылается на 12 модулей,
которых на ПК не существует и в таком виде не может существовать. Идея Phase 2 —
собрать **DLL-заглушки** с теми же именами модулей и тем же набором экспортов,
чтобы связывание прошло, а движок получал *управляемый отказ* (S_OK/NULL), а не
крах.

## Метод сборки

- Списки экспортов каждой заглушки сняты **поимённо из import-таблицы самого
  exe** — состав и регистр совпадают на 100%.
- Все заглушки — валидные PE64 DLL, собранные вручную (без компилятора C/C++:
  побайтовый генератор PE64 + ассемблерный шим на GNU as), верифицированы
  pefile и objdump (формат pei-x86-64).
- Подавляющее большинство функций — простейший `xor eax, eax; ret`
  (возврат 0 = S_OK/NULL).
- DLL размещаются рядом с exe: поиск DLL в Windows начинается с каталога
  приложения.

## Функциональные исключения (реально работают на Windows)

- **xmem.dll**: `XMemAlloc` / `XMemAllocDefault` → `VirtualAlloc(NULL, size,
  MEM_COMMIT|MEM_RESERVE, PAGE_READWRITE)`; `XMemFree` / `XMemFreeDefault` →
  `VirtualFree(p, 0, MEM_RELEASE)`; `XMemVirtualAlloc` — прямой проброс в
  `VirtualAlloc`. Это позволило памяти движка реально выделяться под Windows.
- **d3d12_xs.dll**: `D3D12SerializeVersionedRootSignature` — не заглушка, а
  PE-экспорт-форвардер на настоящую системную `d3d12.dll`. Остальные — return 0.

Дизайн-принцип: процесс не должен падать на первом же вызове заглушки. Каждый
вызов возвращает контролируемое значение, и движок либо продолжает
инициализацию, либо завершается управляемо.

## Результат

Симуляция загрузчика подтвердила: все 12 модулей находятся, все 110 экспортов
связываются, `STATUS_DLL_NOT_FOUND` больше не возникает. Подробности —
в [04-loader-simulation.md](04-loader-simulation.md).
